# 项目迁移清单（同机换盘 · 2026-10-24 实测）

> **适用场景**：同一台 Windows 机器，把项目从当前盘（`D:\WorkBuddyPJ\2026-10-14-10-40-45`）迁到另一个盘。
> **数据来源**：全部为 2026-10-24 对本机工作区、`E:\Git`、MySQL `ry_jxc` 的**实测统计**。
> **一句话结论**：**必须迁移约 13 MB**（不含 Redis）或 **约 60 MB**（含 Redis 免安装包）；**不要迁移约 380 MB**（`target` 89M + `node_modules` 244M + `dist` 7.3M + Vite 缓存 23M）；此外还有 **4 项工作区之外的资产**需要单独处理。

---

## 一、总体判定（一页看完）

| 判定 | 内容 | 体积 |
|---|---|---|
| ✅ **必须迁移** | `RuoYi-Vue`（排除 `**/target`）、`RuoYi-Vue3`（排除 `node_modules`/`dist`）、`sql/`、`docs/`、根目录 3 份 md | **≈13 MB** |
| 🟡 **建议迁移** | `.workbuddy/memory/`（项目约定与会话记忆）、`D:\ruoyi\uploadPath`（上传文件） | ≈60 KB |
| 🟡 **按需迁移** | `codegen/`（生成器留档 848 KB）、`redis/`（免安装 Redis 47 MB） | ≈48 MB |
| ❌ **不要迁移** | `target/`、`node_modules/`（含 `.vite` 缓存）、`dist/`、`*.log`、`codegen/*.zip` | ≈363 MB |
| 🔗 **工作区之外，需单独处理** | MySQL 服务库 `ry_jxc`、`D:\home\ruoyi\logs`、`D:\ruoyi\uploadPath`、`E:\Git` 仓库 | DB 2.2 MB / 日志 493 KB / 上传 52 KB / 仓库 8.6 MB |

> 全量目录约 **420 MB**，白名单只占 **3%**。换盘时**优先复制白名单**，产物到新盘重新生成——这是唯一能避免「jar 锁、缓存路径、依赖损坏」三重坑的做法。

### ② 构建 / 编译产物（❌ 不迁移、❌ 不入版本、✅ 可重新生成）

|---|---|---|---|

## 五、迁移步骤（同机换盘，8 步）

| 步骤 | 操作 | 校验点 |
|---|---|---|
| 1 | **先 push Git**（`E:\Git` 有 1 个未推送提交） | `git status` 显示 `main...origin/main` 无 ahead |
| 2 | 备份数据库：`mysqldump -u root -p ry_jxc > backup\ry_jxc_20261024.sql` | 文件 ≈ 1–2 MB |
| 3 | 停三件套：前端 Ctrl+C、后端 `taskkill /PID <8080进程>`、Redis 关窗口 | 6379/8080/80 无监听 |
| 4 | 按白名单 robocopy 复制（排除 target/node_modules/dist/.git/*.log） | 目标目录 ≈13 MB（含 redis 则 ≈60 MB） |
| 5 | 改 3 处路径配置（logback、application.yml profile、如需则 druid）+ 文档路径替换 | `grep -r "D:/WorkBuddyPJ" docs` 应为空 |
| 6 | 重建依赖：`cd RuoYi-Vue3 && npm install`（**首次生成 package-lock.json**）；如需后端：`mvn package -DskipTests`（先停 8080） | `node_modules` 重建成功、无 EBADENGINE 警告 |
| 7 | 启动：Redis（新路径）→ 后端（`env -u SERVER__PORT java -jar ... --server.port=8080`）→ 前端 `npm run dev` | 见下方 6 项校验 |
| 8 | 观察 1 周无问题后清理旧盘 | 旧盘目录打包留档或删除 |

## 六、注意事项（8 条，均有实测依据）

1. **⚠️ 仓库有未推送提交**：`E:\Git` 当前 `main` 比 `origin/main` **ahead 1**（`6255dce feat(ui): 品牌替换为商超管理系统 + SVG 猫图标 + 商超欢迎页` 尚未 push）。**迁移前必须先推送**，否则换盘即丢这次改造。
2. **⚠️ 前端没有 `package-lock.json`**：`RuoYi-Vue3` 只有 `package.json`，`npm install` 可能拉到与当前不同的次版本（Vue 3.5 / Vite 6 / Element Plus 2.13 均为区间声明）。**迁移时首次生成并提交 lock 文件**，后续才可复现。
3. **⚠️ `.vite` 缓存带绝对路径**：`node_modules/.vite`（23 MB）是跨盘复制的头号故障源，表现为启动报「Failed to resolve import」→ 直接删除整个 `node_modules` 重装最稳。
4. **⚠️ 配置打包在 jar 内**：`ruoyi-admin.jar`（86 MB）内含 `application*.yml`，改路径后不重打包 = 白改；或用 `--spring.config.location` 外置。
5. **⚠️ 两个工作区外的目录容易漏**：`D:\ruoyi\uploadPath`（上传文件）与 `D:\home\ruoyi\logs`（业务日志）。只复制项目目录，头像/附件会 404。
6. **⚠️ 老环境坑在新盘依旧成立**：宿主注入 `SERVER__PORT`（值动态，10-21 实测 3827，历史 9514）→ 必须 `env -u SERVER__PORT` + `--server.port=8080`；`http_proxy` 同为动态注入 → `curl` 一律加 `--noproxy '*'`。
7. **⚠️ Redis 无持久化**：实测 `redis/` 下无 `.rdb/.aof`，重启即清空缓存与登录 token（用户需重新登录）。**业务数据全在 MySQL，不受影响**——不需要为 Redis 做数据迁移。
8. **⚠️ `codegen/*.zip` 是冗余中间产物**：11 个 zip 与 11 个解压目录内容重复，源码中已有最终落位文件；只留目录或干脆不迁都不影响运行。

## 七、迁移后校验 checklist（6 项，可直接执行）

```bash
# 1. 三件套端口监听
netstat -ano | grep -E ":(6379|8080|80) " | grep LISTENING
# 2. 后端存活
curl -s -o /dev/null -w '%{http_code}\n' --noproxy '*' http://localhost:8080/captchaImage   # 期望 200
# 3. 登录链路
curl -s --noproxy '*' -X POST http://localhost:8080/login -H "Content-Type: application/json" \
     -d '{"username":"admin","password":"admin123"}' | head -c 120                          # 期望 code:200 + token
# 4. 业务数据在位（期望 total=4）
curl -s --noproxy '*' -H "Authorization: Bearer <token>" "http://localhost:8080/jxc/stock/list?pageNum=1&pageSize=5"
# 5. 前端 + 品牌标题
curl -s --noproxy '*' http://localhost/ | grep -o '<title>.*</title>'                       # 期望 商超管理系统
# 6. 上传目录生效（登录后访问任意头像 URL，或直接看文件是否存在）
ls "E:/ruoyi/uploadPath"
```

**验收标准**：1–5 全部通过即视为迁移成功；第 6 项失败只影响头像/附件显示，改 `application.yml` 的 `profile` 并重打包即可。
