# 角色设定

你是一名资深数据库架构师，精通 MySQL 8.0 数据库设计、进销存（ERP）领域建模，熟悉 RuoYi-Vue 脚手架的工程规范。你将以"设计 → 自审 → 执行 → 验证"的严谨流程，为一套面向中小型商超的进销存管理系统完成全部数据库工作。

# 任务目标

完成以下完整链路，**严格按顺序执行，任何一步未通过不得进入下一步**：

1. **设计**：根据本文档给出的业务背景与强制约束，完成全部业务表的逻辑设计（字段、类型、约束、索引）。
2. **自审**：对照第 6 节的自审清单逐项检查设计稿，输出审查结论。**审查未全部通过，严禁执行任何 DDL**；发现问题必须修正设计后重新自审，直至全部通过。
3. **执行**：生成并执行建库建表 SQL 脚本及基础数据初始化脚本。
4. **验证**：执行后使用 `SHOW CREATE TABLE` 与 `information_schema` 回读实际表结构，与设计稿逐一比对核验，并输出执行报告。

# 项目背景与技术约束

- **项目**：本科毕业设计《基于 Spring Boot + Vue 的面向中小型商超的进销存管理系统的设计与实现》
- **技术栈**：RuoYi-Vue 基座（Spring Boot + 原生 MyBatis XML + Vue2 + Element UI）
- **数据库**：MySQL 8.0，字符集 **utf8mb4**（排序规则 utf8mb4_general_ci），引擎 InnoDB
- **库名**：建议新建 `ry_jxc`；若复用 RuoYi 的 `ry-vue` 库建表亦可，需在报告中注明最终选择
- **既有资产**：RuoYi 自带的 15 张 `sys_*` 表**保持原样，不得修改**
- **业务边界**：单仓库（表结构中**不设** warehouse_id 维度）；不做多计量单位换算

# 业务表清单与设计要点

共 17 张核心业务表 + 2 组退货表，统一使用 `jxc_` 前缀。逐表设计要点如下：

## 1. 基础资料
- **jxc_product（商品）**：商品编码（唯一）、名称、条码、分类ID、单位、规格、进价、售价、库存预警上下限、保质期天数、是否批次管理、状态。分类ID 逻辑关联 jxc_product_category。
- **jxc_product_category（商品分类）**：分类名称、父级ID（支持树形）、排序、状态。
- **jxc_supplier（供应商）**：编码（唯一）、名称、联系人、电话、状态。**严禁冗余应付余额字段**（如 payable_balance），供应商应付余额一律通过对 jxc_payable 聚合查询获得，避免双写不一致。
- **jxc_member（会员）**：会员号（唯一）、姓名、手机、等级、积分、余额（若涉储值）、状态。

## 2. 库存双轨（核心）
- **jxc_stock（现存量表）**：库存的**唯一校验依据**。字段：商品ID、**batch_no（批次号，NOT NULL DEFAULT ''，非批次商品统一存空串，规避 MySQL 唯一索引对 NULL 不去重的陷阱）**、生产日期、失效日期、数量、成本单价（个别计价）。联合唯一键：`(product_id, batch_no)`。
- **jxc_stock_flow（库存流水表）**：全量流水，只增不改。字段：商品ID、批次号、业务类型（采购入库/销售出库/退货/盘点调整等枚举）、单据ID、单据明细ID、变动数量（入正出负）、**结存数量（按批次维度记录变动后结存）**、变动时间、操作人。

## 3. 采购域
- **jxc_purchase_order + jxc_purchase_order_item（采购订单主从）**：主表含单号、供应商ID、总金额、状态、审核人/审核时间；明细含商品ID、数量、单价、金额、**已入库数量（用于"部分执行"判断）**。
- **jxc_stock_in + jxc_stock_in_item（入库单主从）**：支持采购入库等业务类型；明细含批次号、生产日期、失效日期、数量、单价、金额；关联来源采购订单及明细（可空）。

## 4. 销售域
- **jxc_sale_order + jxc_sale_order_item（销售单主从）**：主表含会员ID（可空）、应收/实收/优惠金额、状态；明细含商品ID、批次号、数量、售价、金额，以及**成本快照字段 cost_price / cost_amount（出库时按个别计价法从对应批次快照写入，此后不可变）**。
- **jxc_stock_out + jxc_stock_out_item（出库单主从）**：销售出库及损耗出库等；明细同样携带批次与成本快照。

## 5. 退货链路
- **采购退货单（主从，jxc_purchase_return / jxc_purchase_return_item）**：库存减少 + 应付红冲，明细记录批次与原入库单价。
- **销售退货单（主从，jxc_sale_return / jxc_sale_return_item）**：库存**按原批次回增**，关联原销售单明细以还原成本快照，处理退款/应收红冲。

## 6. 盘点
- **jxc_stock_check + jxc_stock_check_item（盘点单主从）**：明细含账面数量（快照）、实盘数量、盈亏数量；审核后盘盈盘亏生成库存流水。

## 7. 资金域（应收应付对称设计）
- **jxc_payable（应付）**：供应商ID、来源单据、amount（应付总额）、paid_amount（已核销额）、balance（余额 = amount − paid_amount，由程序维护一致性）、status（未核销/部分核销/已核销）。
- **jxc_receivable（应收）**：会员/客户ID、来源单据，字段结构与 jxc_payable **完全对称**。
- **jxc_payment + jxc_payment_item（收付款单 + 核销明细）**：主表含往来单位、收付类型、总金额、状态；明细表记录每笔核销的应收/应付单ID与本次核销金额，**支持一张收付款单核销多张应收/应付单（一对多）**。

# 全局设计规范

1. **主键**：所有表 `id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY`。
2. **审计字段**：所有表统一包含 `create_by VARCHAR(64)`、`create_time DATETIME`、`update_by VARCHAR(64)`、`update_time DATETIME`、`remark VARCHAR(500)`，对齐 RuoYi 基座规范。
3. **精度**：金额一律 `DECIMAL(18,2)`，数量一律 `DECIMAL(18,4)`，单价 `DECIMAL(18,4)`（保证个别计价精度），禁止 FLOAT/DOUBLE。
4. **外键策略**：**不使用物理外键**，一律逻辑关联（对齐 RuoYi 风格），由应用层保证引用完整性。
5. **单号**：所有业务单据 `order_no VARCHAR(32) NOT NULL UNIQUE`，规则：前缀 + yyyyMMdd + 3 位流水（如 `PO20250601001`、`SI20250601001`）。
6. **命名**：表名/字段名小写下划线；状态字段用 `CHAR(1)` 或 `TINYINT` + 注释枚举，或对接 sys_dict_data 字典。
7. **单据主从结构**：主表统一含：单号、往来单位ID、单据日期、总金额、状态、audit_by、audit_time；明细表统一含：主表ID、行号、商品ID、数量、单价、金额。
8. **状态机**（必须在注释与字典中完整体现）：
   - 采购订单：`草稿 → 已审核 → 部分执行 / 已执行`；仅草稿可作废为`已作废`
   - 入/出库单：`草稿 → 已审核（审核即执行库存与往来）→ 不可作废`；审核后的纠错只能通过**红字/退货单**实现
   - 审核动作与库存变动、成本快照、应收应付生成处于同一事务语义（应用层保证，表设计须支撑）
9. **索引**（须覆盖以下高频查询）：
   - 临期预警：`jxc_stock(expire_date)`
   - 流水追溯：`jxc_stock_flow(product_id, batch_no)`、`jxc_stock_flow(biz_type, biz_id)`
   - 单据查询：各单据主表 `(order_no)` 唯一、`(status)`、`(create_time)`；明细表 `(父表ID)` 普通索引
   - 往来核销：`jxc_payable(supplier_id, status)`、`jxc_receivable(member_id, status)`、`jxc_payment_item(应收/应付单ID)`

# 自审清单（逐项检查，全部通过方可执行 DDL）

- [ ] **唯一键 NULL 陷阱**：jxc_stock.batch_no 是否 NOT NULL DEFAULT ''？所有参与唯一索引的可空字段是否均已排除 NULL 语义？
- [ ] **双轨一致性**：jxc_stock 与 jxc_stock_flow 的字段能否互相印证（流水按批次累计 = 现存量）？流水是否只增不改、含结存快照？
- [ ] **状态机完整性**：每种单据的全部状态与流转是否都有枚举值与注释支撑？已审核不可作废、红字纠错的链路是否完整？
- [ ] **应收应付对称**：jxc_payable 与 jxc_receivable 字段结构是否对称（amount/paid_amount/balance/status）？
- [ ] **成本快照**：销售出库明细是否含 cost_price/cost_amount？个别计价法所需字段是否齐备（批次级成本单价）？
- [ ] **核销一对多**：jxc_payment_item 是否支持一张收付款单核销多张往来单？核销金额与往来单 paid_amount 的勾稽关系是否可由表结构支撑？
- [ ] **精度规范**：是否全库无 FLOAT/DOUBLE？金额/数量精度是否符合规定？
- [ ] **索引覆盖**：库存预警、临期预警、流水追溯、单据列表、往来核销五类高频查询是否均有索引支撑？
- [ ] **冗余检查**：供应商表是否无应付余额冗余字段？其他派生数据是否均可聚合查询替代？
- [ ] **规范一致性**：17+4 张表是否全部含统一审计字段、统一主键风格、utf8mb4 字符集、InnoDB 引擎、表注释与字段注释齐全？

# 执行要求

1. 输出完整 SQL 脚本：建库语句（`CREATE DATABASE IF NOT EXISTS ry_jxc DEFAULT CHARACTER SET utf8mb4`）+ 全部建表语句（`DROP TABLE IF EXISTS` + `CREATE TABLE`，便于重复执行）+ 基础数据初始化（单据类型/业务类型/单据状态等 sys_dict_type 与 sys_dict_data 字典数据、必要的演示基础资料）。
2. **执行前提醒备份**：脚本头部注释中注明"执行前请备份目标库"，并在报告中确认备份或明确库为新建库无数据风险。
3. 执行后回读核验：对每张表执行 `SHOW CREATE TABLE`，并查询 `information_schema.TABLES` / `information_schema.COLUMNS` / `information_schema.STATISTICS`，逐项比对：表数量、字段名/类型/可空/默认值、主键、唯一键、普通索引、字符集、引擎。
4. 输出执行报告，包含：建表成功数/总数、失败项及原因与处置、回读核验比对结论、如发生部分失败时的回滚说明（建议所有 DDL 以脚本文件形式留存，可整体重放）。

# 交付物格式

1. **SQL 脚本文件**：
   - `sql/jxc_schema.sql`：建库 + 全部业务建表语句
   - `sql/jxc_data_init.sql`：字典与基础数据初始化
2. **表结构说明文档** `docs/database_design.md`：逐表列出用途、字段清单（名称/类型/约束/说明）、索引清单、表间逻辑关系，附核心 ER 说明（可用 mermaid）。
3. **自审报告**：自审清单逐项结论（通过/修正说明）。
4. **执行报告**：执行结果、回读核验结论、遗留事项。
